# Что вставить в базу после ревизии 12.08.2026

Коротко: **два файла**, по очереди, через Supabase → SQL Editor. Оба безопасно вставлять
повторно. Ничего удалять и откатывать не нужно.

Времени — минут десять вместе с проверками.

---

## Порядок

### Шаг 1. `supabase/migrations/2026-08-12_core_rls_baseline.sql`

Открыть файл, скопировать **целиком**, вставить в SQL Editor, нажать Run.

**Что должно вывестись.** Четыре строки NOTICE, и все четыре — «ничего не менялось»:

```
NOTICE:  Функции RLS: все на месте, ничего не создавалось.
NOTICE:  RLS: уже включён на всех четырёх таблицах.
NOTICE:  Политики: все 12 на месте, ничего не создавалось.
NOTICE:  Гранты: табличного UPDATE у authenticated/anon нет — ничего не менялось.
```

и в конце строка со словами `core RLS baseline`.

Это ожидаемый результат: на работающем проде файл не меняет ничего. Он нужен на будущее —
чтобы базу можно было поднять из репозитория, если она когда-нибудь потеряется.

> **Если увидите «СОЗДАНЫ», «ВКЛЮЧЁН (был выключен!)» или «УЖЕСТОЧЕНЫ» — остановитесь
> и напишите разработчику.** На живом проде такого быть не должно: это значит, что в базе
> чего-то не хватало, и надо разобраться почему, прежде чем идти дальше.

## Проверка, что применилось

Вставьте это одним куском в SQL Editor. Здесь только чтение, ничего не меняется.

```sql
-- 1. Обе функции в новой редакции
select proname as "функция",
       case when prosrc like '%@round12%' then 'round12 ОК' else 'СТАРАЯ — не применилось' end as "редакция"
  from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'public' and proname in ('guard_bases_update', 'my_visible_types')
 order by 1;
```

Ожидание — ровно две строки, в обеих `round12 ОК`:

| функция | редакция |
|---|---|
| guard_bases_update | round12 ОК |
| my_visible_types | round12 ОК |

```sql
-- 2. Триггер на месте
select tgname as "триггер"
  from pg_trigger t join pg_class c on c.oid = t.tgrelid
 where c.relname = 'bases' and t.tgname = 'guard_bases_update';
```

Ожидание — **одна** строка: `guard_bases_update`.

```sql
-- 3. Триггерную функцию нельзя дёрнуть снаружи
select coalesce(array_to_string(proacl, ', '), 'PUBLIC — ПЛОХО') as "кому доступна"
  from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'public' and proname = 'guard_bases_update';
```

Ожидание — строка вида `postgres=X/postgres`. Слов `anon`, `authenticated` и `PUBLIC`
в ней быть не должно.

```sql
-- 4. RLS включён на всех таблицах без исключения
select c.relname as "таблица без RLS"
  from pg_class c join pg_namespace n on n.oid = c.relnamespace
 where n.nspname = 'public' and c.relkind = 'r' and not c.relrowsecurity;
```

Ожидание — **ноль строк**. Любая строка здесь означает открытую наружу таблицу.

```sql
-- 5. Двенадцать базовых политик на месте
select tablename as "таблица", count(*) as "политик"
  from pg_policies
 where schemaname = 'public'
   and tablename in ('bases', 'base_members', 'profiles', 'tasks')
 group by 1 order by 1;
```

Ожидание:

| таблица | политик |
|---|---|
| base_members | 4 |
| bases | 2 |
| profiles | 2 |
| tasks | 4 |

```sql
-- 6. У обычных пользователей нет табличного UPDATE на profiles и bases
select table_name as "таблица", grantee as "роль"
  from information_schema.role_table_grants
 where table_schema = 'public' and table_name in ('profiles', 'bases')
   and grantee in ('anon', 'authenticated') and privilege_type = 'UPDATE';
```

Ожидание — **ноль строк**. (Колоночный доступ при этом остаётся: `bases.settings`
и `profiles.display_name` — так и задумано.)

## Что именно чинится, человеческим языком

**Первое — защита имени базы.** В базе стоял триггер, который должен был запрещать
хозрабочему переименовывать базу и уводить её в чужой отряд. Он был написан с ошибкой
и не срабатывал **вообще ни разу**: проверка «это служебный вызов?» всегда отвечала «да»
и пропускала любого. Дыры при этом не было — имя базы держал отдельный запрет на уровне
колонок, — но защита была одинарной там, где задумывалась двойная. Теперь триггер работает
по-настоящему: проверено на тестовой базе, хозрабочий получает отказ, начальник участка
переименовывает как и раньше, а Edge Function работает без изменений.

**Второе — список баз.** Одна из служебных функций (`my_visible_types`, её вызывают
политики склада) отдавала перечень идентификаторов **всех** баз организации любому, кто
просто вошёл в приложение, — даже человеку без единой базы и без должности. Ни остатков,
ни названий, ни имён — только идентификаторы и их количество. Всё равно лишнее. Теперь
функция показывает только те базы, к которым человек причастен. Проверено, что видимость
склада у механика, повара, хозрабочего, начальника участка и бухгалтера при этом не
изменилась ни на одну позицию.

**Третье, на будущее.** Настройки доступа четырёх таблиц (`bases`, `base_members`,
`profiles`, `tasks`) до сих пор существовали только внутри живой базы, а в репозитории
их не было. Если бы базу пришлось поднимать заново, эти таблицы поднялись бы **без
защиты** и любой вошедший смог бы сделать себя владельцем. Теперь они записаны в
репозиторий, и файл умеет их восстановить.

## Что осталось незакрытым (решать вам)

1. **DDL самих таблиц по-прежнему не в репозитории.** Файл `core_rls_baseline` включает
   защиту и заводит политики, но `create table` для `bases`, `profiles`, `base_members`,
   `tasks`, `stock_items`, `journal_entries`, `parties`, `org_roles` в каталоге нет.
   Полное восстановление «с нуля» одним лишь репозиторием пока невозможно —
   нужен ещё дамп схемы. Стоит один раз выгрузить `pg_dump --schema-only` и положить
   рядом. Это разовая работа минут на двадцать.

2. **`RBAC_SCHEMA_SNAPSHOT.sql` и `2026-07-08_rls_functions_snapshot.sql` — не исполняемые.**
   Первый почти целиком закомментирован, во втором пропущены точки с запятой между
   функциями и одна функция ссылается на другую до её создания. Как справочник они
   работают, как файл для вставки — нет. Я их не трогал: сейчас это даже защищает
   (случайная вставка не откатит ничего), но и восстановить по ним нельзя. Если решите
   привести в порядок — скажите, сделаю отдельно.

3. **`app_private` не должна попадать в настройку PostgREST.** Функция
   `app_private.journal_row_type` умеет отдать вид имущества по любой базе, и её спасает
   только то, что схема `app_private` не указана в «Exposed schemas» проекта
   (Settings → API). Проверьте, что там по-прежнему `public, graphql_public`, и не
   добавляйте туда `app_private`.

4. **Заголовок `cf-connecting-ip`** обе Edge Function принимают на веру. Пока весь трафик
   идёт через Cloudflare — это верно. Если появится путь в обход, ограничение частоты
   на восстановление пароля можно будет обойти. Сейчас менять ничего не нужно, просто
   имейте в виду.

## Если что-то пошло не так

Оба файла завёрнуты в транзакцию: при ошибке не применяется **ничего**, база остаётся
в прежнем состоянии. Можно спокойно исправить причину и вставить заново.

Если файл ругается «Сначала примените …» — значит не хватает предыдущего файла из
`supabase/migrations/README.md`, п. 2. Это не поломка, а именно то, ради чего проверки
и добавлены: раньше такие случаи проходили молча и расходились тихо.
