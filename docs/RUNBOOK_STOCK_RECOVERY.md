# Что делать, если остатки склада обнулились или позиции пропали

Короткая инструкция на случай инцидента. Спокойно, данные восстановимы: с 2026-07-30
каждое изменение остатка/партий пишется в `public.stock_history` (предыдущее значение).

---

## 0. Сначала: а точно ли пропали?

**Позиции не исчезают из поиска при нулевом остатке.** `renderStockList` фильтрует по типу,
категории и сроку, но НЕ по наличию — позиция с `qty=0` остаётся в списке, просто помечена
«Нет в наличии», зачёркнута и уходит вниз.

Значит, если позиция **вообще не находится** поиском — это НЕ обнуление, смотрите раздел 4.
Если находится, но всё в «Нет в наличии» — это обнуление, разделы 1–3.

Чего лишается обнулённая позиция: она не попадает в счётчики чипов («Все», «Продукты» и т.д.),
в плитку продуктов на дашборде и в фильтры «Просрочка»/«Скоро» — они по смыслу считают только наличие.

---

## 1. Зафиксировать масштаб (ничего не меняя)

`base_id` берётся из «Ещё → Базы» или из `bases`.

```sql
-- что ушло из «>0» в «0» за последние 48 часов
select * from public.stock_zeroing_report('<base_id>', 48);

-- сколько всего
select count(*) from public.stock_zeroing_report('<base_id>', 48);
```

В отчёте есть `changed_by` — кто внёс правку (`null` = бэкенд/service_role). Это помогает понять,
инцидент это или осознанное списание. Колонка `status`: `zeroed` — строка на месте и обнулена
(восстанавливается автоматически, §3); `deleted` — строки больше нет, её нужно вернуть вручную (§4.3).

Обе функции (`stock_zeroing_report`, `stock_qty_restore`) доступны **только** из SQL Editor /
Management API (service_role) — из приложения их вызвать нельзя (проверено: `anon` и `authenticated`
получают `forbidden` даже если кто-то вернёт им грант).

Колонка `status` в отчёте:
- `zeroed` — строгий ноль, восстанавливается автоматически (§3);
- `near_zero` — остаток упал ниже 1% от прежнего, но не в ноль: возможен и саботаж, и легальный
  расход почти под ноль. Автоматически НЕ восстанавливается — решает человек;
- `deleted` — строки больше нет, вернуть можно только вручную (§4.3).

История фиксирует не только остаток и партии, но и смену `type`/`name`/`unit` — иначе массовая
«пересортица» (сменить `type` у 3000 позиций и спрятать их от повара через `can_see_type`, не тронув
остатки) не попадала бы ни в отчёт, ни в откат.

## 2. Выбрать точку возврата

```sql
-- когда пошли обнуления
select min(changed_at), max(changed_at)
from public.stock_history
where base_id = '<base_id>' and qty > 0
  and changed_at > now() - interval '48 hours';
```

Берите момент **чуть раньше** первого обнуления.

## 3. Восстановить

Сначала ВСЕГДА «на сухую» (`true` — ничего не меняет, только показывает список):

```sql
select * from public.stock_qty_restore('<base_id>', '2026-07-30 12:00:00+00', true);
```

Если список выглядит правильно — применить (`false`):

```sql
select * from public.stock_qty_restore('<base_id>', '2026-07-30 12:00:00+00', false);
```

⚠️ **Важное ограничение (не пропустите).** Критерий «пострадавших» — остаток равен нулю СЕЙЧАС.
Отличить «обнулено инцидентом» от «легально списано в ноль после инцидента» функция не может,
а списание в ноль — самая частая обычная правка. Поэтому:

- сверяйте dry-run по колонке `changed_by` (кто правил), а не «на глаз»;
- ограничивайте окно инцидента четвёртым параметром `p_until` — правки позже него не откатятся:

```sql
-- откатить только то, что сломалось между 12:00 и 12:20, не трогая позднюю работу смены
select * from public.stock_qty_restore('<base_id>', '2026-07-30 12:00:00+00', false, '2026-07-30 12:20:00+00');
```

Свойства, на которые можно опираться:

- Восстанавливаются **только позиции со строгим нулём**. Дробный остаток (например 0.0005 кг специй)
  НЕ затирается — он показывается в отчёте как `near_zero` и требует решения человека.
- **Идемпотентно**: повторный запуск не портит уже восстановленное (вернёт 0 строк).
- Работает **только от владельца** (`is_admin`) или из бэкенда (service_role). Остальным — `forbidden`.
- Изоляция по базе: чужую базу функция не трогает.

После восстановления в облаке — на устройствах сделайте «Ещё → Обновить базу из облака»,
чтобы клиенты подтянули восстановленные остатки (иначе локальная копия может снова выгрузить нули).

## 4. Позиция вообще не находится поиском

Тогда это не обнуление. Проверяйте по порядку:

1. **Тип и роль.** Механик видит только `tool`, повар — `product`+`household` (RLS `can_see_type`).
   Позиция чужого типа не видна вообще. Проверьте роль в «Ещё → Работники».
2. **Не та база.** Поиск идёт по активной базе. Проверьте чип базы в шапке.
3. **Позиция удалена.** Удаления тоже в истории:
   ```sql
   select * from public.stock_history
   where base_id='<base_id>' and op='delete'
     and name ilike '%часть имени%'
   order by changed_at desc;
   ```
   Восстановление удалённой СТРОКИ (не остатка) — вручную `insert` из снимка истории.
4. **Снят со смены / нет прав.** При `isOffShift` RLS вернёт пусто; клиент это распознаёт
   и не затирает локальные данные, но список будет пустым.

## 5. Профилактика

- `stock_history` держит 180 дней; ретеншн — `select public.stock_history_prune(180);`
  Поставьте по расписанию (pg_cron), иначе таблица растёт (пишется только при РЕАЛЬНОМ
  изменении `qty`/`batches`, поэтому обычный синк её не раздувает).
- `CHECK (qty >= 0)` добавлен как `NOT VALID` (новые записи проверяются, старые — нет).
  Когда убедитесь, что отрицательных остатков нет, провалидируйте:
  ```sql
  alter table public.stock_items validate constraint stock_items_qty_nonneg;
  ```
- Жёсткий запрет на массовое обнуление НЕ ставили осознанно: клиент выгружает чанками по 100 строк,
  поэтому порог «больше N обнулений за один запрос» либо рвёт легальную выгрузку (порог ≤100),
  либо не срабатывает вовсе (порог >100 — инцидент пройдёт по 100 за раз). Гарантия здесь —
  восстановимость, а не запрет.
- Клиентский страж `suspectWipe` ловит массовое **удаление** (осталось <10% позиций от снимка),
  но не обнуление — он считает число позиций, а не остатки. История закрывает именно этот пробел.
