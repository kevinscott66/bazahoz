до последнего байта.

**Отпечаток — это тождество приложения.** Любая будущая сборка обязана давать тот же
отпечаток; другой отпечаток означает другой ключ и, для телефона, другое приложение.
Проверять так:

```bash
apksigner verify --print-certs vahtahoz-<версия>.apk
```

## Что внутри

**Оболочка едет внутри файла** (с 03.08.2026, см. «Офлайн» ниже). Собирает бандл
`scripts/build-native-www.sh`: `vahtahoz.html`, `supabase.js`, `xlsx.js`,
`manifest.webmanifest`, `sw.js` и надстройку `native/packaged.js` — в `native/www`,
откуда `npx cap sync android` кладёт их в `assets/public`. В CI шаг стоит **до** `cap sync`.

Адрес приложения задаётся не `server.url`, а `server.hostname = vahta.razvedchick.ru`
при `androidScheme = https`: локальные файлы отдаются по тому же адресу, по которому
раньше грузился сайт. **Это обязательное условие, а не украшение** — `localStorage`,
сессия входа и кэш привязаны к origin, и смена адреса оставила бы уже установленные
приложения с пустой базой и разлогином. Побочное следствие: внутри приложения весь хост
`vahta.razvedchick.ru` перехвачен локальным сервером и наружу не ходит.

Цена решения: **веб-часть внутри APK застывает** на моменте сборки. Раньше правки
доезжали до приложения сами, теперь — только с новым файлом. Поэтому:

- любой выпуск веб-части, который должен дойти до людей с приложением, требует новой
  сборки APK (`gh workflow run native-android.yml`);
- `native/packaged.js` внутри приложения раз в сутки читает `https://razvedchick.ru/appver.json`
  (его пишет `scripts/build-site.sh` из `APP_BUILD`, руками номер не ведут) и, если живая
  сборка новее носимой, один раз показывает полоску со ссылкой на `/app`. Спрашивается
  **апекс**: `vahta.` изнутри приложения ответил бы своей же копией.
  Для этого в `_headers` у `/appver.json` стоит `Access-Control-Allow-Origin: *` —
  запрос идёт с origin `https://vahta.razvedchick.ru`, без заголовка ответ не отдадут.

## Где лежит для людей

Артефакт GitHub живёт ~90 дней и требует входа в репозиторий, поэтому файл раздаётся с сайта:

- **`https://razvedchick.ru/app`** — страница установки (она же на `vahta.razvedchick.ru/app`).
- **`https://vahta.razvedchick.ru/vahtahoz.apk`** — сам файл, постоянный адрес.
- `https://vahta.razvedchick.ru/vahtahoz.apk.sha256` — сумма для проверки.

**Только `vahta.`, не апекс.** На `razvedchick.ru` действует правило Cloudflare, которое уводит
всё, начинающееся на `/vahtahoz`, на приложение: `razvedchick.ru/vahtahoz.apk` отвечает `301` и
открывает рабочий стол вместо загрузки файла. Правило не трогали — это тот самый короткий адрес,
который называют людям вслух. Ссылки на странице `/app` поэтому абсолютные.

Сам файл лежит в репозитории в `downloads/`, в `dist` его кладёт `scripts/build-site.sh`.
Адрес намеренно **без версии**: ссылка в переписке и на странице не должна протухать при
следующей сборке. При выпуске новой версии меняется четыре места — файл в `downloads/`,
имя в `scripts/build-site.sh`, `Content-Disposition` в `_headers`, а также версия, сумма
и отпечаток на `site/app.html` и в этом документе.

## Офлайн

**Версии до 1.0.7 включительно офлайн не открывались вообще.** Причина: APK был окном на
живой сайт (`server.url`), внутри лежала заглушка на 340 байт, а WebView не даёт service
worker'у перехватывать переход на саму страницу — то есть `sw.js`, который держит офлайн
в браузере, в обёртке страницу поднять не мог. Нет сети — нет запуска.

С 03.08.2026 оболочка лежит внутри файла, и запуск от сети не зависит: WebView открывает
`https://vahta.razvedchick.ru/` из `assets/public` (перехват идёт до всякой сети, DNS и TLS
не участвуют). Проверено на собранном бандле 02.08.2026, до сборки APK:

- `index.html` (заглушка на 124 байта) уводит на `./vahtahoz.html`; переход локальный;
- `sw.js` встаёт и прекэширует все четыре обязательных файла — то есть набор внутри APK
  полный, ничего не потерялось при копировании;
- при равных номерах сборок полоски обновления нет, при подставленном `v999` — есть;
- **с погашенным сервером** (мёртвый порт, не эмуляция «offline») приложение открывается
  и рисует дашборд.

Чего эта проверка не покрывает: она сделана в обычном браузере на собранном каталоге
`native/www`, а не на телефоне. **Проверку в самолётном режиме на живом аппарате
делает владелец** — здесь нет ни устройства, ни эмулятора.

### Что проверить на телефоне

Два пути, и они проверяют разное. Второй важнее: у людей уже стоит 1.0.7.

**Путь А — чистая установка** (телефон, где приложения не было):

1. Поставить `vahtahoz-1.0.8.apk`, открыть, войти при связи, полистать «Склад» и «Задачи».
2. Закрыть приложение полностью (из списка недавних), включить **самолётный режим**.
3. Открыть заново. Ожидание: открывается рабочий стол со списками, гейта входа нет.
   Провал: белый экран, «страница недоступна», экран входа.
4. Не выходя из самолётного режима — отметить приход или расход, закрыть, открыть снова:
   запись на месте. Выключить самолётный режим — запись уезжает в облако.

**Путь Б — поверх 1.0.7** (обновление, как у людей):

1. На телефоне с 1.0.7 и данными — поставить 1.0.8 поверх, **не удаляя** старое.
2. Открыть при связи: вход не спрашивают, склад и задачи на месте (значит origin сохранился
   и `localStorage` не потерялся — это главное, что проверяет путь Б).
3. Дальше пункты 2–4 из пути А.

Отдельно: полоска «вышло обновление». Она появляется, только когда живая сборка новее
носимой, не чаще раза в сутки и один раз на номер. Сразу после выпуска её быть не должно
(номера равны) — это правильное поведение, а не поломка. Проверить её можно будет на
следующем выпуске веб-части: с сетью, при первом открытии после выкатки.

Известная неизвестность в пути Б: при обновлении переживает не только `localStorage`,
но и **зарегистрированный старый service worker** (он ставился с живого сайта и
привязан к тому же origin). На переход на саму страницу он не влияет — WebView его туда
не пускает, оболочка в любом случае берётся из `assets/public`. Дальше рассуждение
без проверки: подчинённые запросы (`supabase.js`, `xlsx.js`, `packaged.js`) пойдут через
старый обработчик, `supabase.js` и `xlsx.js` у него в кэше лежат, `packaged.js` — нет.
Худшее, что из этого следует, — на обновлённом телефоне какое-то время не показывается
полоска обновления. Запуск офлайн от этого не страдает ни в одной ветке. Если путь Б
покажет иначе — это находка, и её надо записать сюда.

Первый вход офлайн невозможен по-прежнему: `gateEarly()` показывает гейт при отсутствии
`vahtahoz_sess`, режима «без облака» в приложении нет. То есть офлайн-запуск работает
начиная со второго открытия — после входа, сделанного при связи.

Браузерная линия офлайн работает тоже, и это проверено 02.08.2026 на живом коде:
после первой загрузки `caches` содержит `vahtahoz-v260` с четырьмя записями; при **погашенном
сервере** (не эмуляция «offline», а мёртвый порт) перезагрузка отдаёт оболочку v260 из кэша,
`window.supabase` поднимается из кэша, интерфейс рисуется. С лежащей в `localStorage` сессией
— даже просроченной на час — гейт входа не показывается и открывается дашборд.

Что из этого следует для совета людям на странице `/app`: офлайн теперь умеют **оба**
способа, и выбор идёт по трафику. Браузерная первая загрузка ≈ 611 КБ сжатыми (оболочка 260
+ `xlsx` 295 + `supabase` 52 + мелочь), причём критична только оболочка — 260 КБ, остальное
догружается позже (`Promise.allSettled` + явная проверка `SHELL` в `sw.js`). APK — единый
файл в несколько мегабайт, оборвался на середине — качать заново целиком. Поэтому там, где
интернета в обрез, по-прежнему советуем браузер и значок на главный экран.

Настоящее автообновление веб-части внутри APK (скачать свежую оболочку и открывать её
вместо носимой) сознательно **не делалось**: это подмена документа на лету, проверить её
без живого телефона нельзя, а цена ошибки — приложение, которое не открывается ни офлайн,
ни онлайн. Вместо этого — честная полоска «вышло обновление».

## Установка поверх отладочной сборки

Отладочные APK **никому, кроме владельца, не раздавались** (подтверждено владельцем
02.08.2026), поэтому в инструкции для людей этого случая нет — на странице `/app` про
переустановку не написано ничего.

Сам факт остаётся в силе для владельца: подпись — тождество приложения, отладочный ключ
и ключ владельца дают для телефона разные приложения, поверх не встанет («пакет конфликтует
с существующим»). Порядок на своём телефоне: выгрузка данных → удаление (**данные при
удалении пропадают**) → установка `vahtahoz-1.0.7.apk` → вход и загрузка выгрузки обратно.

Дальше обновления идут поверх обычным порядком, потому что ключ уже не меняется.

## Ключ подписи: единственная копия

Хранилище лежит только в секретах GitHub Actions (`ANDROID_KEYSTORE_BASE64`,
`ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`, добавлены 31.07.2026).
Секреты **не читаются обратно** ни через веб, ни через API — ни человеком, ни агентом.
Копии `.jks` на рабочем маке нет (искал).

Чем это грозит: если секрет удалят или потеряют доступ к репозиторию, **обновлять
установленное приложение станет нечем** — только удаление у всех и установка заново с потерей
данных. Ключ действует до 2053 года, то есть это риск не на месяц, а навсегда.

Что с этим можно сделать — решение владельца:

- Достать хранилище обратно разово: временный workflow, который пишет
  `ANDROID_KEYSTORE_BASE64` в артефакт, владелец скачивает и кладёт в надёжное место, workflow
  удаляется. Цена: ключ на 90 дней лежит в артефакте, доступном всем, у кого есть чтение
  репозитория. Репозиторий приватный, но это всё равно вынос ключа наружу.
- Оставить как есть и полагаться на сохранность репозитория и секретов.

Схемы подписи v3 у сборки нет, поэтому штатная смена ключа (rotation) недоступна: при утрате
ключа пути «подписать новым, телефон примет» не будет.
