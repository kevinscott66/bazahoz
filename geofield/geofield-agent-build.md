# GeoField — многоагентная сборка и состязательная проверка

Документ о том, **как строить программу**, а не что она делает. Идея: не один агент пишет всё подряд, а флот специализированных субагентов под управлением оркестратора, где часть агентов намеренно настроена **спорить друг с другом** и искать дыры в логике, заглушки и несоответствия. Применимо к любому проекту, не только к GeoField.

---

## 1. Принцип

Один агент, пишущий код в одиночку, страдает тремя болезнями: пишет заглушки и «потом доделаю», не замечает противоречий между модулями, и не критикует сам себя всерьёз. Лечится это **разделением ролей и состязательностью**: тот, кто пишет, и тот, кто рвёт написанное на части, — разные агенты с разными мандатами.

Схема — диалектическая:

```
ТЕЗИС            АНТИТЕЗИС               СИНТЕЗ
реализатор  →  критики (несколько,  →  арбитр сводит
пишет код      разные мандаты,         разногласия и
               спорят и ищут дыры)     выносит решение
```

Ключевое: критики **не должны соглашаться по умолчанию**. У каждого свой угол атаки и явная инструкция «найди, почему это плохо», а не «оцени, хорошо ли это».

---

## 2. Три механизма Claude Code, на которых это строится

1. **Субагенты** (`.claude/agents/*.md`) — переиспользуемые роли: свой системный промпт, своя модель, свои права на инструменты. Работают внутри родительской сессии, экономны по токенам. Это основа — ростер ролей.
2. **Agent Teams** (экспериментальные, с Opus 4.6) — оркестратор и воркеры в **отдельных** контекстных окнах, общаются между собой, держат общий список задач. Команда 2–16 агентов. Включается переменной окружения. Нужны для реально параллельной работы над общей базой.
3. **Динамические воркфлоу** («ultracode», нужна свежая версия Claude Code) — оркестрация вынесена из контекста в код, Claude — планировщик, а не диспетчер. Масштабируется на сотни агентов и держит порядок стадий. Нужны, когда конвейер проверки фиксированный и длинный.

**Правило выбора:** до 3–5 параллельных задач — обычная схема «оркестратор + субагенты». Больше — обязательно код-оркестрация (ultracode), иначе контекст оркестратора забьётся отчётами и он потеряет нить.

## 3. Ростер агентов

Часть ролей у тебя уже есть как пользовательские скиллы — их можно прямо переиспользовать (указано в скобках).

**Управление:**
- **Оркестратор** — разбивает задачу на куски, раздаёт, собирает результаты, выносит финальное решение «влить / вернуть». Самая сильная модель (Opus). Держать его контекст **чистым**: он принимает короткие вердикты, а не простыни.

**Производство:**
- **Архитектор** — проектирует модуль/контракт интерфейсов до написания кода (можно `deep-research` для разбора вариантов).
- **Реализатор** — пишет код по утверждённому контракту (`coding-agent`). Может быть несколько параллельно, каждый в своей ветке/worktree.

**Состязательная проверка (ядро системы):**
- **Критик-разрушитель** (`brutal-expert`) — атакует решение: где сломается, что не предусмотрено, какой более сильный вариант. Прямо, без смягчения.
- **Аудитор логики** — ищет **несоответствия между модулями**: контракт обещает одно, реализация делает другое; два модуля по-разному понимают одну сущность; граничные случаи (пустой керн, нулевой интервал, проба без привязки).
- **Охотник за заглушками** — отдельный, узкий мандат: найти всё, что притворяется готовым. TODO, FIXME, `return null`/`pass` вместо логики, подменные данные в проде, замоканные ответы, пустые catch, «happy path без обработки ошибок», функции-пустышки. Это **барьер**: ничего с заглушками не проходит дальше.
- **Аудитор производительности** — проверяет против бюджетов из ТЗ (раздел 10): не сломан ли холодный старт, не течёт ли память, не тянет ли список всё в память, не растолстела ли синхронизация.
- **Безопасник** — секреты в коде, инъекции, лишние права, утечки в логи.

**Контроль качества:**
- **Тестировщик** — пишет и гоняет тесты; для мобильных — на реальных устройствах (`ios-real-device-tester`, `android-real-device-tester`, `mobile-real-device-tester`).
- **Рефакторщик** — дубли, мёртвый код, переусложнение, единообразие стиля.

**Чтобы агенты не разъезжались:**
- **Хранитель контекста** — держит единый источник правды: контракты интерфейсов, модель данных, бюджеты, словарь терминов. Все агенты сверяются с ним, а не с памятью.

## 4. Конвейер сборки одной задачи

```
1. ПЛАН          Оркестратор разбивает фичу на куски, пишет контракты,
                 кладёт их к Хранителю контекста.

2. РЕАЛИЗАЦИЯ    Реализаторы пишут код в изолированных ветках (git worktree —
                 чтобы параллельные агенты не дрались за одну ветку).

3. ПАРАЛЛЕЛЬНЫЙ   Несколько критиков с РАЗНЫМИ мандатами проверяют один и тот
   АУДИТ          же код независимо, не видя выводов друг друга (чтобы не было
                 «стадного» согласия). Каждый возвращает короткий вердикт:
                 ПРОШЛО / НАШЁЛ ПРОБЛЕМЫ (список с местами в коде).

4. БАРЬЕР         Охотник за заглушками + Аудитор логики — это жёсткие ворота.
   ЗАГЛУШЕК/      Хоть одна заглушка или логическое противоречие — стоп,
   ЛОГИКИ         возврат на доработку. Без обсуждения.

5. СОСТЯЗАНИЕ     Если критики разошлись во мнениях — Арбитр (роль оркестратора)
                 выслушивает аргументы сторон и выносит решение, фиксируя
                 ПОЧЕМУ (в журнал решений).

6. ТЕСТЫ          Тестировщик гоняет автотесты + проверку на реальном
                 устройстве для мобильных кусков.

7. ВЕРДИКТ        Оркестратор: влить / вернуть на доработку с конкретным
                 списком. Цикл повторяется, пока барьеры не пройдены.
```

---

## 5. Мандат «никаких заглушек» (конкретно)

Охотник за заглушками заваливает проверку, если находит:

- `TODO`, `FIXME`, `HACK`, «временно», «потом доделаю»;
- функцию, которая возвращает заглушечное значение вместо реальной работы;
- подменные/захардкоженные данные там, где должны быть настоящие;
- замоканные ответы сети/базы вне тестов;
- пустой `catch`/проглоченную ошибку;
- ветку «на случай ошибки», которой нет (только happy path);
- закомментированный код «чтобы не потерять».

Исключения только явные и помеченные: настоящие тестовые подмены **в тестах**, заглушки за выключенным feature flag (и то — с записью в реестр незавершённого).

---

## 6. Как заставить агентов реально спорить, а не поддакивать

- **Разные мандаты, а не разные имена.** Критик-разрушитель и аудитор логики должны иметь несовместимые цели: один ищет «сломается под нагрузкой», другой — «противоречит контракту». Тогда они находят разное.
- **Слепота к чужим выводам на этапе аудита.** Критики проверяют независимо; их отчёты сводятся только у арбитра. Иначе первый же вердикт «вроде норм» заражает остальных.
- **Запрет на вежливость в промпте критика.** Прямая инструкция: «твоя задача — найти, почему это не сработает; если не нашёл серьёзной проблемы — копай глубже, а не пиши „выглядит хорошо“».
- **Арбитр требует доказательств.** Не «мне кажется», а «вот строка, вот сценарий, вот что сломается».

## 7. Защита от типичных провалов агентных систем

| Провал | Лечение |
|---|---|
| Контекст оркестратора забивается отчётами субагентов (после 3–5 параллельных) | Перейти на код-оркестрацию (ultracode); субагенты возвращают короткие вердикты, не простыни |
| Claude осторожен с параллелизмом по умолчанию | Указывать число явно: «три критика, по одному на модуль» |
| «Слишком умная» оркестрация — семь стадий там, где хватит трёх | Ограничивать число агентов в промпте, упрощать |
| Параллельные агенты дерутся за git-ветку | Каждому свой worktree |
| Дорого: каждое сообщение между агентами — обращение к модели | Воркеры на дешёвой модели (Sonnet/Haiku), оркестратор и арбитр — на Opus |
| Агенты «забыли» общую модель данных и разъехались | Единый источник правды у Хранителя контекста, сверка с ним обязательна |

## 8. Распределение моделей (цена/качество)

- **Оркестратор и арбитр** — сильная модель (Opus). Они принимают решения и сводят споры — тут экономить нельзя.
- **Критики и аудиторы** — средняя (Sonnet). Их много, они работают параллельно.
- **Рутина** (форматирование, мелкий рефакторинг, прогон тестов) — лёгкая модель (Haiku).

## 9. Пример определения субагента (`.claude/agents/`)

Охотник за заглушками — узкий, злой, с правами только на чтение и поиск:

```markdown
---
name: stub-hunter
description: Находит заглушки, недоделки и подменные данные в проде. Барьер перед вливанием.
model: sonnet
tools: [read, grep, glob]   # только чтение — он не правит, он находит
---

Ты — охотник за заглушками. Твоя единственная задача — найти всё,
что притворяется готовым кодом, но им не является.

Ищи: TODO/FIXME/HACK, функции-пустышки, return-заглушки вместо логики,
захардкоженные данные вместо реальных, замоканные сеть/базу вне тестов,
проглоченные ошибки (пустой catch), отсутствие обработки ошибок,
закомментированный код.

Формат ответа — строго:
ВЕРДИКТ: ПРОШЛО | НАШЁЛ ЗАГЛУШКИ
СПИСОК: файл:строка — что именно и почему это заглушка

Не оценивай качество архитектуры — это не твоя работа.
Не предлагай решений. Только находки. Если чисто — так и скажи коротко.
```

Критик-разрушитель (можно опереть на твой существующий скилл `brutal-expert`):

```markdown
---
name: red-team
description: Атакует решение и ищет, где оно сломается. Без смягчения.
model: opus
tools: [read, grep, glob]
---

Ты — разрушитель. Цель: доказать, что это решение плохое или сломается.
Не хвали. Не пиши «выглядит хорошо». Если не нашёл серьёзной проблемы —
копай глубже: нагрузка, граничные случаи, поле без связи, мороз, обрыв
синхронизации на середине, конфликт правок двух геологов.

Каждое возражение подкрепляй: где именно (файл:строка) и какой сценарий
это ломает. «Мне кажется» не принимается.
```

Включение командного режима (Agent Teams) — переменной окружения перед запуском сессии; точную переменную и версию сверь в актуальной документации Claude Code, она меняется.

## 10. С чего начать тебе конкретно

1. У тебя половина ростера уже есть как пользовательские скиллы (`coding-agent`, `brutal-expert`, `deep-research`, тестировщики устройств) — переоформи их в `.claude/agents/` с узкими мандатами и форматами вердиктов.
2. Допиши недостающих: `stub-hunter`, `logic-auditor`, `perf-auditor`, `context-keeper`.
3. Начни без громоздкой оркестрации: оркестратор + 3 критика на каждый кусок MVP (раздел 8 ТЗ). Поймёшь ритм — подключишь Agent Teams для параллели и ultracode для длинного конвейера.
4. Барьер заглушек и логики поставь с первого дня — именно он отделяет «работающий MVP» от «демки, которая разваливается в поле».
