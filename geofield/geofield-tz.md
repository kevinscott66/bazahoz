# Полевое геологическое приложение — детальный план

**Рабочее название:** GeoField (условно)
**Суть:** кросс-платформенный инструмент сбора первичной геологической информации, спроектированный «от поля», а не «от офиса». Один код — на Windows, macOS, Linux, Android и iOS. Работает неделями без связи, бережёт батарею и спутниковый канал, ловит ошибки в момент ввода и сам сводит пробы с лабораторией.

---

## 0. Главный принцип

Приложение на 80% живёт в поле и на 20% в офисе. Всё, что геолог вводит в маршруте, вводится **один раз** и больше никогда не перебивается руками. Офис не «командует» полем — он принимает то, что поле собрало, и готовит данные для тяжёлых систем подсчёта запасов (Micromine, ГЕОМИКС, Datamine).

Из этого принципа вытекают три жёстких правила, которые нельзя нарушать ни ради красоты, ни ради «удобства разработки»:

1. **Связи нет по умолчанию.** Наличие связи — редкое событие, а не фон. Любая функция обязана работать офлайн.
2. **Данные не теряются никогда.** Падение, разрядка, мороз, выдернутая батарея — после перезапуска всё на месте. Автосохранение после каждого действия, а не по кнопке «Сохранить».
3. **Ошибка ловится при вводе, а не в камералке через месяц.** Противоречие нельзя ввести физически.

## 1. Технологическая основа

### 1.1. Чем собирать интерфейс (одно ядро на 6 платформ)

**Рекомендация: Flutter.**

Почему именно он для этой задачи:

- Рисует интерфейс собственным движком (Impeller), а не системными виджетами и не веб-вью. Это даёт пиксельно одинаковую картинку на всех платформах и полный контроль над внешним видом — то, что нужно, чтобы уйти от шаблонного вида и сделать собственную визуальную идентичность.
- Мобильная часть — самая зрелая среди единых движков. Для приложения, где телефон/планшет в поле — главное устройство, это решающий аргумент.
- Десктоп поддерживается стабильно (Windows/macOS/Linux), один код покрывает все шесть целей.
- Отличная офлайн-база: SQLite через `drift` (типобезопасные запросы, миграции, реактивность).
- 60 кадров по умолчанию — анимации, которые «объясняют», а не тормозят на слабом железе.

**Чем платим:** язык Dart (придётся освоить), экосистема библиотек меньше, чем у JS.

**Альтернативы — честно:**

- **Compose Multiplatform (Kotlin)** — бери, если ближе Kotlin/Android-мир. Полное разделение интерфейса между платформами, стабильный iOS-таргет вышел в 2025. Зрелость десктопа чуть ниже Flutter.
- **Tauri 2 + веб-фронт (Rust под капотом)** — ты его уже знаешь по карточкам для маркетплейсов. Десктоп — превосходный, крошечный вес. Но мобильная часть «юзабельна, но всё ещё догоняет». Для приложения, которое живёт в поле на телефоне, это слишком большой риск на главной платформе. Хороший запасной вариант, если вдруг решишь сделать поле = планшет/ноутбук, а телефон — второстепенным.

### 1.2. Локальная база на устройстве

- **SQLite** — стандарт офлайн-хранения, годами проверенный, держит гигабайты, работает на всех платформах. Через `drift` в Flutter.
- Все таблицы версионируются (миграции схемы), потому что формы документации будут меняться, а старые данные ломать нельзя.

### 1.3. Карты и геопространство

- **MapLibre GL** — открытый движок карт, офлайн-тайлы (растровые и векторные) грузятся дома и работают без связи. Без вендора и без обязательного интернета.
- Космоснимки и топооснова кэшируются регионами заранее.
- Пересчёт координат — библиотека на базе `proj4`: WGS-84, СК-42, проекция Гаусса–Крюгера, местные МСК. Конвертация внутри, без ручных плясок.

### 1.4. Серверная часть (минимальная)

- **Postgres** в защищённом контуре (камералка или твой основной узел) — мастер-база.
- **Relay-узел** на дешёвом внешнем VPS (или твой fly.io-баланс) — публичная точка приёма синхронизации. Полевые устройства не ходят напрямую в камеральную базу; они стучатся в relay, а тот через обратный туннель (WireGuard) пробрасывает в защищённый контур. Ровно та архитектура, что ты уже строил.
- На relay — лёгкий сервис приёма дельт (Go или Rust: один бинарь, мало памяти).

## 2. Модель данных (что вообще хранится)

Иерархия сущностей — от крупного к мелкому. Каждая запись имеет: `id` (UUID, генерируется на устройстве, чтобы не было коллизий при офлайн-работе), `автор`, `создано`, `изменено`, `версия`, `статус синхронизации`.

```
Проект (месторождение/участок)
└── Партия / отряд
    └── Маршрут (день работы конкретного геолога)
        ├── Точка наблюдения
        │   ├── Описание породы/обнажения
        │   ├── Структурные замеры (азимут, угол падения)
        │   ├── Пробы (привязаны к точке)
        │   └── Фотографии
        └── Скважина
            ├── Интервалы документации керна (от–до)
            │   ├── Описание литологии
            │   ├── Структурные замеры по керну
            │   ├── Пробы (привязаны к интервалу)
            │   └── Фотографии ящиков керна
            └── Инклинометрия (если есть)

Проба (сквозная сущность с собственным жизненным циклом):
  тип (керн / шлам / шлих / почвенная / бороздовая / штуфная)
  → штрихкод/QR (печатается на бирку)
  → статус: отобрана → упакована → отправлена в лабораторию → результат получен
  → результаты анализов (элементы, содержания, метод, дата)

Справочники (управляемые, версионируемые):
  породы, цвета, минералы, типы изменения, типы проб, лаборатории, ед. измерения
```

Ключевая идея: **проба — главная единица учёта.** Всё крутится вокруг того, чтобы мешок в поле, строка в базе и результат из лаборатории всегда указывали друг на друга через штрихкод, без ручной сверки таблиц.

## 3. Синхронизация между устройствами

### 3.1. Поток

```
[Телефон геолога А]  ─┐
[Телефон геолога Б]  ─┼─► [Relay-узел (VPS)] ═══обратный туннель═══► [Postgres камералки]
[Планшет на буровой] ─┘                                                      │
                                                                            ▼
[Ноутбук камералки] ◄──── читает из той же мастер-базы, готовит выгрузку в Micromine/ГЕОМИКС
```

### 3.2. Два способа — выбери под аппетит к контролю

**Вариант А — готовый движок (быстрее запуститься).**
PowerSync: двусторонняя синхронизация Postgres ↔ локальный SQLite, есть Flutter-SDK, в начале 2026 на проде ощущался стабильнее конкурентов. Сам решает доставку, чекпоинты, частичную репликацию. Минус — зависимость от стороннего сервиса/самостоятельного хостинга его слоя.

**Вариант Б — собственный журнал изменений (лучше ложится на тонкий спутниковый канал, рекомендую как целевой).**
Принцип — *event sourcing*: устройство ведёт **append-only лог мутаций** (каждое действие = запись «создал точку X», «изменил поле Y», «отобрал пробу Z»). Синхронизация — это обмен логами, а не состояний.

Почему это правильно для спутника:
- Уходит только **дельта** — что нового с прошлого сеанса. Не вся база.
- Лог **сжимается** (он текстово-структурный, жмётся отлично) и режется на пакеты.
- **Возобновляется с места обрыва** — связь упала на середине, продолжили с того же пакета. Ровно логика твоих ватчдогов.
- Вес трафика — приоритет номер один. Фото уходят отдельной очередью, по одному, в самую последнюю очередь и только когда канал стабилен (можно вручную поставить «фото не отправлять до камералки»).

### 3.3. Конфликты

Большинство данных конфликтов не порождает: каждый геолог владеет своими точками и пробами — там работает «последняя запись побеждает» по метке времени. Конфликт возможен только если двое правят одну общую запись (например, описание одной скважины). Тогда:

- по умолчанию — последняя запись побеждает, но **старая версия не стирается**, а уходит в историю;
- спорные поля помечаются флажком «требует решения» и всплывают в камералке для ручного разбора;
- для полей, которые реально редактируют совместно, можно подключить CRDT (`cr-sqlite`) — но это усложнение, и без явной нужды его не вводим.

### 3.4. Журнал изменений (аудит)

Кто, что, когда внёс и поправил — хранится всегда. Нужно и для контроля качества (QA/QC), и чтобы понимать, чьим данным верить. Видно прямо в карточке записи.

## 4. Дизайн-система

Цель: интерфейс выглядит **сделанным вручную и под конкретную задачу**, а не собранным из стандартных компонентов и не «сгенерированным». Тренд 2026 тут помогает: ставка на ясность с собственным почерком, типографику, которая дышит, и движение, которое объясняет структуру, а не украшает.

### 4.1. Что делает вид «из 2000-х» и как этого избежать

| Признак «2000-х» | Что делаем вместо |
|---|---|
| Серые объёмные кнопки с градиентом и тенью-вдавленностью | Плоские, но с ясной иерархией: цвет = значимость, не объём |
| Меню-«ёлка» с десятками пунктов | Контекстные действия, появляются по месту работы |
| Подписи ко всему мелким шрифтом | Крупная типографика, воздух, одно главное действие на экран |
| Серо-синяя «офисная» палитра | Своя палитра с доменным смыслом (см. ниже) |
| Иконки из стандартного набора | Собственная иконография под геологию (керн, обнажение, проба, маршрут) |

### 4.2. Что делает вид «нейросетевым» и как этого избежать

- Не использовать дефолтную тему Material/готовых наборов как есть — она узнаётся мгновенно. Своя тема, свои токены.
- Не лепить фиолетово-синие градиенты и «glow». Цвет должен иметь функцию (тип пробы, статус синхронизации), а не декоративную.
- Не ставить скругления всюду одинаковыми. Своя система радиусов и отступов.
- Реальная сетка и ритм отступов, а не «на глаз».
- Один характерный, осмысленный шрифт вместо безликого дефолта.

### 4.3. Токены (конкретно)

**Шрифты.** Основной — гротеск с хорошей читаемостью на солнце и поддержкой кириллицы (например, **Inter** или **Manrope** для интерфейса). Для чисел и таблиц (глубины, координаты, содержания) — **моноширинный** (например, **JetBrains Mono**): цифры выстраиваются столбиком, ошибки видны сразу.

**Палитра — доменная, не декоративная:**
- Фон тёмный по умолчанию (экономит батарею на OLED, меньше слепит ночью).
- Один акцентный цвет действия (например, тёплый янтарный) — только для главной кнопки экрана.
- Цвета как **семантика типов проб**: керн / шлам / шлих / почва / борозда — каждому свой устойчивый цвет, одинаковый во всём приложении (и на бирках, и на карте, и в таблицах).
- Статус синхронизации цветом: не отправлено / в очереди / отправлено / подтверждено.
- Статус валидации: ошибка — отчётливо, но не «кровавый» красный, чтобы не утомлять.

**Радиусы/отступы.** Единая шкала (например, 4–8–12–16–24). Кнопки в поле — крупные, минимум 56 px высотой (палец в перчатке).

**Движение.** Анимации короткие (150–250 мс) и функциональные: подсказывают, куда «уехала» запись, что синхронизация пошла, что поле принято. Никаких декоративных переливов.

### 4.4. Два режима экрана (не «тёмная/светлая тема» ради моды, а ради поля)

- **Ночь/сумерки** — тёмный фон, приглушённый акцент, низкая яркость.
- **День на снегу** — отдельный высококонтрастный режим: почти чёрное на почти белом, жирный шрифт, максимальная читаемость под прямым солнцем на снегу. Это не инверсия обычной светлой темы, а специально нарисованный режим.

### 4.5. Режим «перчатки»

Тумблер в настройках: увеличивает все цели нажатия, убирает мелкие жесты, заменяет тонкие свайпы крупными кнопками, включает подтверждение важных действий (чтобы случайно не удалить пробу замёрзшим пальцем).

## 5. Навигация и разница «телефон ↔ десктоп»

Один код, но раскладка адаптируется под устройство.

**Телефон (главный полевой режим):**
- Нижняя панель с 3–4 крупными вкладками в зоне большого пальца: **Карта**, **Сбор**, **Маршрут/Журнал**, **Синхрон.**
- Всё важное — в нижней половине экрана (верх не достаёт большой палец).
- Главное действие экрана — одна большая кнопка снизу.

**Планшет (буровая, документация керна):**
- Двухпанельно: слева список интервалов/проб, справа форма ввода. Видно контекст и ввод одновременно.

**Десктоп (камералка):**
- Полноценные таблицы, разрезы, карты опробования, массовые операции, выгрузка. Многооконность.
- Тут «офисные» 20% задачи.

Переход между платформами — через ту же синхронизацию: начал на телефоне в поле, вечером открыл на ноутбуке — всё на месте.

## 6. Экраны — до кнопки

Ниже каждый ключевой экран: что на нём, что делает каждый элемент, какая логика.

### 6.1. Запуск и выбор контекста

При первом входе — выбор проекта/участка и роли (геолог / документатор / контролёр ОТК / камеральщик). Роль определяет, какие экраны и права видны.

**Элементы:**
- Список проектов (карточки: название, участок, дата последней синхронизации).
- Кнопка «Открыть» на карточке.
- Внизу: индикатор «N записей не отправлено» + кнопка перехода к синхронизации.
- Иконка профиля/роли в углу.

**Логика:** выбранный проект запоминается; повторный запуск открывает сразу карту последнего проекта.

### 6.2. Карта — главный экран в поле

**Что на экране:**
- Карта (офлайн-тайлы), текущая позиция (точка с «усами» точности GPS).
- Точки наблюдения, скважины и пробы — значками своих цветов (семантика типов).
- Линия пройденного маршрута за сегодня.

**Кнопки и элементы (по местам):**
- **Правый нижний угол — большая кнопка «＋ Точка»** (главное действие). Долгое нажатие — меню: точка / скважина / быстрая проба.
- Правый край, столбик мелких кнопок: «моё местоположение» (центрировать), слои карты (топо/спутник/геология), линейка/измерение расстояния.
- Левый верх: текущие координаты в выбранной системе (тап — сменить систему координат), точность GPS (цвет: зелёный/жёлтый/красный).
- Верх по центру: название маршрута и счётчик «точек сегодня».
- Тап по значку на карте — карточка объекта (открыть/редактировать/добавить пробу/фото).

**Логика:**
- Координаты берутся с приёмника **автоматически**, но в карточке точки всегда есть поле для **ручного ввода** (слабый сигнал — вбил вручную).
- Если GPS «плавает», приложение предупреждает и не даёт молча записать мусорную координату.

### 6.3. Точка наблюдения — форма ввода

Открывается после «＋ Точка». Форма разбита на сворачиваемые блоки, чтобы не пугать длиной.

**Шапка:**
- Номер точки (автонумерация по маршруту, можно переопределить).
- Координаты (автоподстановка + ручная правка), высота.
- Время (автоматически).

**Блок «Описание»:**
- Тип объекта: обнажение / закопушка / делювий / коренной выход… (выбор из справочника).
- Порода: поиск по справочнику с подсказками (начал печатать — предложило). Нельзя ввести породу, которой нет в справочнике проекта, но можно добавить с пометкой «на проверку».
- Цвет, зернистость, степень изменения — управляемые списки + свободное поле «примечание».
- Минерализация: чек-боксы минералов + поле интенсивности.

**Блок «Структура»:**
- Азимут падения / угол падения. Ввод вручную или кнопка «снять с датчика» (использует магнитометр+акселерометр устройства как электронный компас, с предупреждением о магнитных помехах от железа).

**Блок «Пробы»** — кнопка «＋ Проба» (см. 6.5).
**Блок «Фото»** — кнопка «＋ Фото» (см. 6.6).

**Низ экрана:**
- Большая кнопка **«Готово»** (но запись уже сохранена автоматически — это просто «свернуть и вернуться к карте»).
- Слева мелко: «Удалить точку» (с подтверждением, в режиме перчаток — двойным).

**Валидация на лету:** обязательные поля подсвечиваются; пока тип породы не выбран, точка помечается жёлтым «черновик», но **не теряется**.

### 6.4. Документация керна

Главный экран на буровой. На планшете — две панели.

**Левая панель — колонка интервалов скважины:**
- Вертикальная шкала глубины.
- Интервалы (от–до) полосками своих литологий (цвет).
- Кнопка «＋ Интервал» внизу.

**Правая панель — ввод по выбранному интервалу:**
- Поля «От (м)» и «До (м)» — крупные, моноширинные.
- Литология (справочник с подсказками).
- Выход керна (%) — можно вводить, можно считать автоматически из замеренной длины.
- Структурные замеры по ориентированному керну, расчёт **истинных углов залегания на лету**.
- Пробы по интервалу (кнопка «＋ Проба»).
- Фото ящика керна.

**Логика — критично:**
- Интервалы **не должны налезать друг на друга и оставлять разрывы**. Если ввёл «от 12.0», а предыдущий кончился на 11.8 — приложение сразу подсвечивает разрыв 0.2 м и предлагает либо закрыть его, либо подтвердить осознанно.
- Глубины проверяются: «до» не может быть меньше «от», интервал не может выходить за забой скважины.
- Рейтинги (Jr и пр.) считаются прямо при вводе, если включён геомеханический режим.

### 6.5. Регистрация пробы и печать бирки

Открывается из точки или интервала. Самый важный для целостности экран.

**Элементы:**
- Тип пробы (крупные кнопки-плитки цветами семантики: керн / шлам / шлих / почва / борозда / штуф).
- Привязка: автоматически к текущей точке или интервалу (показано вверху, можно сменить).
- Номер пробы — автогенерация по схеме проекта (префикс участка + сквозной номер), правится вручную.
- Глубина/интервал отбора (для керна — подтягивается из интервала).
- Масса/длина (если нужно).
- **Штрихкод/QR** — генерируется автоматически из номера. Большая кнопка **«Печать бирки»** (отправка на полевой bluetooth-принтер этикеток) и **«Показать код»** (вывести на экран, если принтера нет — сфотографировать/наклеить от руки).
- Примечание.

**Логика:**
- Один тап «＋ Проба» в типовом случае создаёт пробу с уже заполненными привязкой, глубиной и номером — геологу остаётся подтвердить. Минимум движений на холоде.
- Статус пробы стартует с «отобрана». Дальше: «упакована» → «отправлена» → «результат получен».
- Список проб можно выгрузить как **ведомость отправки в лабораторию** (см. 6.9).

### 6.6. Фотографии

- Съёмка прямо из приложения (или выбор из галереи).
- Привязка автоматически: к точке / интервалу / пробе, с координатами и временем.
- Подсказка положить в кадр масштабную линейку/бирку.
- Фото хранятся локально, сжимаются для синхронизации, уходят **отдельной очередью в последнюю очередь** (чтобы не съесть весь спутниковый канал).
- Можно пометить «не отправлять до камералки» — тогда фото поедут только когда устройство попадёт в нормальный интернет.

### 6.7. Маршрут / Журнал — что собрано

- Список за день/маршрут: точки, скважины, пробы, фото — карточками со статусами.
- Фильтры: только черновики, только с ошибками валидации, только неотправленное.
- Поиск по номеру.
- Тап — открыть запись; свайп — быстрые действия (в режиме перчаток заменяются кнопками).
- Сверху сводка: «12 точек, 34 пробы, 3 черновика, 5 не отправлено».

Это же — точка контроля ОТК: контролёр видит, что заполнено небрежно, и помечает «вернуть на доработку».

### 6.8. Синхронизация — отдельный осознанный экран

Не фоновое требование, а понятное действие, потому что связь — событие.

**Элементы:**
- Большая кнопка **«Синхронизировать»** (активна, только если есть канал; иначе серая с подписью «нет связи»).
- Что уйдёт: «Данных: 248 КБ · Фото: 14 шт. (отдельно)».
- Прогресс по пакетам с возможностью **«Пауза»** и **«Продолжить»** (возобновление с места обрыва).
- Переключатель «отправлять фото сейчас / отложить до камералки».
- Лог последних сеансов: когда, сколько, успех/обрыв.
- Тонкая настройка (для тебя): лимит на пакет, сжатие, приоритет очередей.

**Логика:** при обрыве — не начинать заново; докинуть с последнего подтверждённого пакета. Сначала всегда данные, фото — в хвосте.

### 6.9. Камеральная часть (десктоп)

«Офисные» 20%. Не заменяет тяжёлый 3D-софт, а готовит для него чистые данные.

**Что есть:**
- Таблицы по всем сущностям с фильтрами, массовым редактированием, проверкой целостности по всей базе.
- Простые визуализации: колонка скважины (литология + пробы + содержания), карта опробования, выноска проб на план.
- **Связка с лабораторией:**
  - сформировать ведомость отправки (список проб со штрихкодами) → файл/печать;
  - принять файл результатов из лаборатории → результаты **сами привязываются к своим пробам по штрихкоду**; нестыковки (нет такой пробы, дубль) подсвечиваются для ручного разбора. Это убирает ручную сверку двух таблиц.
- **Выгрузка наружу:** в форматы, которые едят Micromine/ГЕОМИКС, плюс честный CSV/Excel без слетающих полей.
- Разбор конфликтов синхронизации и «черновиков на проверке».
- Полевой журнал и формы — по ГОСТ и привычным образцам, на выходе в печать/PDF.

### 6.10. Настройки

- Системы координат (рабочая по умолчанию + список доступных).
- Справочники проекта (породы, минералы, типы проб, лаборатории) — обновляются с сервера при синхронизации.
- Режим «перчатки», режим «день на снегу», размер шрифта.
- Управление офлайн-картами: какие регионы скачаны, докачать, удалить.
- Принтер бирок (сопряжение).
- Профиль, роль, аккаунт.
- Диагностика синхронизации (лог, размер очередей) — для администратора партии.

## 7. Поведение в суровых условиях (сквозное, на всех экранах)

- **Батарея.** Минимум фоновой активности; экран гаснет агрессивно; GPS опрашивается умно, а не постоянно; никаких лишних анимаций при низком заряде (авторежим энергосбережения).
- **Мороз и внезапное отключение.** Автосохранение после каждого поля. Любой экран можно закрыть в любой момент без потери.
- **Солнце/снег.** Режим высокого контраста (6.4) + крупная типографика.
- **Перчатки.** Режим крупных целей (4.5).
- **Голос.** Диктовка в текстовые поля (описание породы), когда руки заняты или замёрзли. Работает офлайн там, где платформа это позволяет.
- **Карты заранее.** Без скачанных регионов в тайге приложение бесполезно — мастер скачивания карт показывается при создании проекта.

## 8. Дорожная карта (как строить, чтобы не утонуть)

Не пытаться сделать всё сразу. Резать на куски, каждый из которых уже полезен.

**Этап 1 — MVP «электронный полевой журнал» (самое ценное и незакрытое):**
- Карта офлайн + точки наблюдения + пробы со штрихкодом + фото.
- Локальная база, автосохранение, валидация на лету.
- Простая выгрузка в CSV/Excel.
- Один человек, одно устройство. Уже снимает двойной перенос бумага→Excel→база.

**Этап 2 — синхронизация и партия:**
- Журнал изменений, relay-узел, дельта-синхрон по тонкому каналу.
- Несколько геологов в одну базу, разрешение конфликтов.
- Десктоп-камералка (таблицы, контроль целостности).

**Этап 3 — керн и лаборатория:**
- Полноценная документация керна (интервалы, выход, истинные углы).
- Связка с лабораторией по штрихкоду.
- Печать бирок и ведомостей.

**Этап 4 — мост в тяжёлый софт и зрелость:**
- Выгрузка в форматы Micromine/ГЕОМИКС.
- Разрезы, карты опробования.
- ОТК/QA-QC, роли, аудит.

**Этап 5 — масштаб:**
- Свой сервер для корпорации, права, многопартийность.
- Бесплатный режим для одиночки → платный для партии/корпорации.

## 9. Где здесь настоящий рынок

Самый незакрытый кусок — именно **этап 1–2**: автономный полевой сбор первички с умной синхронизацией под тонкий канал для **малых партий и одиночек**. Тяжёлый софт туда не лезет (дорого, тяжело, требует связи и офиса), а академические полевые приложения сырые и без поддержки. Если делать — начинать строго отсюда, а не с красивых 3D-разрезов.

## 10. Оптимизация

Оптимизация — не разовая полировка в конце, а встроенное требование с первого дня. У полевого приложения три ресурса, которые нельзя транжирить: **батарея, спутниковый канал, память слабого устройства.** Под них и затачиваемся.

### 10.1. Бюджеты производительности (целевые цифры)

Задаём заранее и не позволяем превышать. Если правка ломает бюджет — правка не проходит проверку (см. отдельный документ про агентную сборку).

| Показатель | Телефон (поле) | Десктоп (камералка) |
|---|---|---|
| Холодный старт до рабочего экрана | < 2 с | < 3 с |
| Память в покое (карта открыта) | < 250 МБ | < 500 МБ |
| Кадры при прокрутке списка проб | стабильные 60 | 60 |
| Запись точки/пробы (сохранение) | < 50 мс | < 50 мс |
| Размер установщика | < 60 МБ | < 90 МБ |
| Расход батареи: час маршрута с картой и GPS | < 12% заряда | — |
| Объём одной синхронизации (только данные, без фото) | измеряется в сотнях КБ, не МБ | — |

### 10.2. Энергопотребление (главный фронт)

- **GPS по расписанию, а не постоянно.** Опрос приёмника пачками с нужной точностью, а не непрерывный поток. Точность запрашивается под задачу: грубая при перемещении, точная — только в момент фиксации точки.
- **Экран — главный пожиратель.** Тёмный фон на OLED, агрессивное затухание, никаких фоновых анимаций при простое.
- **Никакой лишней фоновой работы.** Синхронизация — только по явному действию или в момент, когда устройство на зарядке и в сети. Никаких «пингов» в пустоту.
- **Авторежим экономии** при заряде ниже порога: гасит анимации, реже опрашивает датчики, откладывает фото.
- **Сжатие — на стороне устройства экономно.** Сжимать дельту стоит (трафик дороже процессора на спутнике), но фото сжимать в момент съёмки один раз, а не пересжимать при каждой попытке отправки.

### 10.3. Канал и синхронизация

- Уходит **только дельта** (журнал изменений), сжатая (zstd/gzip), порезанная на пакеты, возобновляемая.
- **Фото — отдельная очередь, в самом хвосте**, по одному, с возможностью полностью отложить до нормального интернета.
- **Откат при сбое** (экспоненциальная пауза перед повтором) — не долбить мёртвый канал.
- Размер пакета и степень сжатия — настраиваемые (для разных каналов: спутник / слабый сотовый / нормальный интернет).

### 10.4. База данных

- SQLite в режиме WAL (журнал с упреждающей записью) — быстрые записи без блокировок чтения.
- Индексы на всё, по чему ищем (номер пробы, штрихкод, скважина, маршрут).
- Запись пачками (несколько проб — одна транзакция), без N+1.
- Ленивая подгрузка: список проб не тянет в память фото и полные описания, только то, что видно на экране.

### 10.5. Интерфейс и память

- **Виртуализация списков** — на экране только видимые карточки, остальные не существуют в памяти.
- Фото в списках — уменьшенные миниатюры, полный размер только при открытии.
- Карта — векторные тайлы с уровнями детализации; кэш тайлов с лимитом и вытеснением старого.
- Один движок рендера (Impeller у Flutter) даёт предсказуемые 60 кадров без веб-вью-сюрпризов.

### 10.6. Размер и запуск

- Дробление по платформам при сборке (каждая ОС получает только свой код).
- Удаление мёртвого кода при компиляции (tree-shaking).
- Тяжёлые модули (камералка, разрезы) грузятся по требованию, а не при старте.

## 11. Конфигурация на каждом устройстве

Один код — но приложение **узнаёт, на чём запущено, и подстраивается**. Конфигурация многослойная: каждый следующий слой переопределяет предыдущий.

```
Слой 1: значения по умолчанию (в коде)
   ▼ переопределяется
Слой 2: профиль платформы (Android / iOS / Windows / macOS / Linux)
   ▼ переопределяется
Слой 3: класс устройства (определяется на старте: ОЗУ, экран, есть ли GPS/сотовый)
   ▼ переопределяется
Слой 4: настройки проекта (приходят с сервером: справочники, схема нумерации, системы координат)
   ▼ переопределяется
Слой 5: настройки пользователя (перчатки, режим «день на снегу», размер шрифта)
```

### 11.1. Три профиля устройства

**Телефон — «поле».** Карта-главный экран, нижняя панель в зоне пальца, крупные кнопки, агрессивная экономия батареи, фото откладываются, синхрон вручную. Камеральные функции скрыты.

**Планшет — «буровая».** Двухпанельная документация керна (список интервалов + форма), средняя экономия батареи, тот же сбор, что и на телефоне, плюс удобный ввод керна.

**Десктоп — «камералка».** Полные таблицы, разрезы, карты опробования, массовые операции, выгрузка в Micromine/ГЕОМИКС, связка с лабораторией, разбор конфликтов. Экономия батареи не нужна, лимиты памяти выше.

### 11.2. Что определяется автоматически на старте

Приложение замеряет устройство и выставляет config:

- мало ОЗУ → меньше кэш карт, миниатюры жёстче, анимации проще;
- нет модуля GPS (десктоп) → ручной ввод координат как основной;
- нет сотового и нет сети → стартует офлайн, синхрон-кнопка серая;
- маленький экран → раскладка «телефон», большой → «планшет/десктоп».

### 11.3. Как выглядит файл конфигурации (пример)

```yaml
# defaults.yaml — слой 1
sync:
  packet_size_kb: 128
  compression: zstd
  photos: deferred          # фото в хвост очереди
  retry_backoff: exponential
gps:
  mode: scheduled
  precise_only_on_capture: true
ui:
  animations: full
  theme: dark
map:
  tile_cache_mb: 500

# profile.android.yaml — слой 2 (переопределяет)
battery:
  request_optimization_exemption: true   # просить отключить «убийцу фона»
storage:
  scoped: true
location:
  permission: while_in_use

# class.low_ram.yaml — слой 3 (для устройств < 4 ГБ ОЗУ)
ui:
  animations: reduced
map:
  tile_cache_mb: 150
photos:
  thumbnail_quality: low

# project.suzun.yaml — слой 4 (с сервера)
coordinate_systems:
  default: SK-42 / Gauss-Kruger zone 25   # Сусуман ~148° в.д.: ОМ 147° (6·25−3)
  available: [WGS-84, SK-42, MSK-49]
sample_numbering: "SUZ-{seq:05}"
dictionaries_version: 2026-06-12

# user.alex.yaml — слой 5
ui:
  glove_mode: true
  daylight_high_contrast: true
  font_scale: 1.2
```

### 11.4. Особенности по операционным системам

- **Android.** Просить исключение из «оптимизации батареи», иначе система убьёт фон и синхронизацию. Точные разрешения на местоположение (в идеале «только при использовании», постоянное — не злоупотреблять). Раздельное хранилище (scoped storage). Фоновая отправка — через рабочие задачи системы.
- **iOS.** Настоящего фона нет — синхрон только пока приложение активно или в коротких системных окнах. Разрешение на местоположение и камеру с честными пояснениями. Учитывать правила магазина приложений (или распространять корпоративно/через TestFlight, если в магазин не идём).
- **Windows / macOS / Linux.** Разные пути к данным; подпись кода (на macOS — нотаризация, на Windows — сертификат), иначе ОС будет пугать пользователя. Автообновление: на десктопе уместно (полноценные дельта- или полные обновления), в поле — обновлять только по сети, никогда не на спутнике.

### 11.5. Сборки (flavors)

- **field** — полевая, урезанная, без камеральных модулей, максимум экономии.
- **office** — камеральная, полная.
- **dev** — отладочная, с диагностикой и подменными данными (никогда не попадает в поле).

Переключатели функций (feature flags) позволяют включать сырые модули только в dev и не тащить их в полевую сборку.
