# GeoField — протокол дельта-синхронизации

Ядро этапа 2. Целевой вариант из ТЗ (раздел 3.2, вариант Б): **собственный журнал изменений** (event sourcing), заточенный под тонкий спутниковый канал. Не PowerSync — ради полного контроля над трафиком и возобновлением.

Главный приоритет — **вес трафика**. Всё остальное (простота, красота) уступает бюджету канала: один сеанс данных — сотни КБ, не МБ (ТЗ 10.1).

---

## 1. Модель: обмен логами, а не состояниями

Каждое действие пользователя — это запись в append-only `change_log` (см. `schema/001_initial.sql`): «создал точку X», «изменил поле Y пробы Z», «удалил интервал W». Синхронизация — обмен этими логами, а не полными таблицами.

Запись мутации:

```
change_id     UUID     — уникальный id мутации (идемпотентность: повтор не применяется дважды)
entity_table  string   — таблица сущности
entity_id     UUID     — id записи
op            enum      insert | update | delete
payload       JSON     — для insert: полная запись; update: только изменённые поля; delete: {}
author_id     UUID
device_id     UUID
logical_ts    HLC      — гибридные логические часы (см. §4)
```

Почему это правильно для спутника (ТЗ 3.2):
- уходит только **дельта** — что нового с прошлого сеанса, не вся база;
- лог **сжимается** (текстово-структурный, жмётся отлично);
- **возобновляется с места обрыва** — связь упала, продолжили с того же пакета;
- **идемпотентен** — повторная доставка пакета безопасна (`change_id` уникален).

## 2. Топология

```
[Телефон А] ─┐
[Телефон Б] ─┼─► [Relay-узел (VPS)] ══WireGuard-туннель══► [Postgres камералки]
[Планшет]   ─┘        (приём дельт)                          (мастер-база)
```

Полевые устройства не ходят в камеральную базу напрямую — только в relay. На relay — лёгкий сервис приёма дельт (Go/Rust: один бинарь, мало памяти), который валидирует, дедуплицирует по `change_id` и проталкивает в Postgres через обратный туннель.

---

## 3. Сеанс синхронизации

Синхронизация — **явное действие пользователя** (экран 6.8), не фон. Сеанс двусторонний: PUSH локальных мутаций и PULL чужих.

### 3.1. PUSH (устройство → relay)

1. Выбрать из `change_log` записи с `synced = 0`, отсортировать по `seq`.
2. Нарезать на **пакеты** фиксированного размера (`sync.packet_size_kb`, по умолчанию 128 КБ), сжать (`zstd`, ТЗ 11.3).
3. Слать пакеты по порядку. На каждый — relay отвечает `ack` со списком принятых `change_id` и `ack_batch`.
4. По `ack`: пометить эти строки `synced = 1`, проставить `ack_batch`.
5. Обрыв — **не начинать заново**: докинуть с первого неподтверждённого пакета (курсор — максимальный подтверждённый `seq`).

### 3.2. PULL (relay → устройство)

1. Отправить курсор `last_pulled_seq` (из `sync_state`) — что уже получено с сервера.
2. Relay отдаёт чужие мутации новее курсора, теми же сжатыми пакетами.
3. Применять мутации по порядку (см. §5), обновляя `last_pulled_seq` по мере подтверждения пакетов.
4. Обрыв — возобновление с последнего примененного курсора.

### 3.3. Порядок и приоритет

- **Сначала всегда данные, фото — в хвосте** (§6).
- PUSH и PULL в одном сеансе; при узком окне — сперва PUSH (не потерять собранное), потом PULL.
- **Откат при сбое** — экспоненциальная пауза перед повтором (ТЗ 10.3), не долбить мёртвый канал.

---

## 4. Порядок событий и часы (HLC)

Времени устройств доверять нельзя (расходятся, переводят вручную). Порядок мутаций определяется **гибридными логическими часами** (Hybrid Logical Clock): `logical_ts = (физ_время_мс, счётчик)`.

- при каждой локальной мутации HLC инкрементируется;
- при получении чужой мутации локальный HLC подтягивается до `max(local, incoming) + 1`;
- сравнение — сперва по физической части, при равенстве — по счётчику, при равенстве — по `device_id` (детерминированный разрыв ничьи).

HLC даёт устойчивый глобальный порядок без синхронных часов и без центрального счётчика.

---

## 5. Применение чужих мутаций и конфликты

Правило по умолчанию — **последняя запись побеждает** (Last-Write-Wins) по HLC. Большинство данных конфликтов не порождает: каждый геолог владеет своими точками и пробами.

Алгоритм применения входящей мутации `m` к записи:

1. **insert** несуществующей записи → вставить.
2. **insert** уже существующей (повтор доставки) → игнор по `change_id` (идемпотентность).
3. **update/delete**: сравнить HLC. Входящая новее локальной несинхронизированной правки того же поля → применить, **старую версию — в `record_history`** (не стираем). Локальная новее → отклонить входящую, но сохранить как проигравшую в истории.
4. **Реальный конфликт** — двое правили **одно и то же поле** общей записи (например, описание одной скважины) с параллельными (несопоставимыми по причинности) HLC:
   - применяем победителя по LWW;
   - проигравшее значение пишем в `conflicts` с флагом «требует решения»;
   - в камералке (десктоп) оператор разбирает вручную.

Записи, которыми владеет один автор (его точки/пробы/фото), в п. 4 практически не попадают.

> CRDT (`cr-sqlite`) — только для полей, которые реально редактируют совместно, и только при явной нужде. По умолчанию не вводим (ТЗ 3.3): усложнение без выгоды.

## 6. Фото — отдельная очередь

Фото способны съесть весь спутниковый канал, поэтому:

- идут **отдельной очередью, в самом хвосте**, по одному, только когда канал стабилен;
- по умолчанию `defer_until_office = 1` — не отправлять до нормального интернета (можно переопределить на экране синхронизации);
- **сжимаются один раз при съёмке**, а не пересжимаются при каждой попытке (ТЗ 10.2);
- статус — в `photos.upload_status` (`pending → queued → uploaded`), независимо от `sync_status` метаданных;
- метаданные фото (привязка, координаты) — обычные мутации в `change_log` и уходят с данными; сам файл — по своей очереди.

---

## 7. Бюджет и настраиваемость

Из ТЗ 10.1/11.3 — параметры сеанса настраиваются под канал (спутник / слабый сотовый / нормальный интернет):

| Параметр | Ключ конфигурации | По умолчанию |
|---|---|---|
| Размер пакета | `sync.packet_size_kb` | 128 |
| Сжатие | `sync.compression` | `zstd` |
| Фото | `sync.photos` | `deferred` |
| Откат при сбое | `sync.retry_backoff` | `exponential` |

**Контроль:** экран синхронизации показывает объём до отправки («Данных: 248 КБ · Фото: 14 шт.»), даёт паузу/продолжение и лог сеансов. Вес одного сеанса данных **обязан** держаться в сотнях КБ — превышение ловит `perf-auditor` (это провал бюджета, не замечание).

---

## 8. Гарантии и инварианты (проверяет `logic-auditor`)

1. **Ни одной потерянной мутации.** Строка `change_log` помечается `synced = 1` только после `ack` от relay.
2. **Идемпотентность.** Повтор пакета/мутации не меняет состояние (дедуп по `change_id`).
3. **Возобновляемость.** Обрыв на любом пакете → продолжение с последнего подтверждённого, без полного рестарта.
4. **Никакого молчаливого затирания.** Проигравшая версия всегда уходит в `record_history`; спорное поле — в `conflicts`.
5. **Каждая пользовательская мутация → ровно одна запись в `change_log`** и инкремент `version` сущности.
6. **Порядок применения** соответствует HLC; причинность не нарушается.

---

## 9. Этапность

- **Этап 1 (MVP):** `change_log` пишется с первого дня (один пользователь, одно устройство). Сеть не нужна — лог просто копится. Это делает базу sync-ready без затрат сейчас.
- **Этап 2:** поднимается relay, включаются PUSH/PULL, конфликты, история. Схема менять не нужно — таблицы уже заложены в `001_initial.sql`.
