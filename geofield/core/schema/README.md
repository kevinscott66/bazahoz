# Схема локальной базы GeoField — версионирование и миграции

Ядро этапов 1–2. Локальная база на устройстве — **SQLite в режиме WAL**, через `drift` во Flutter. Схема версионируется, потому что формы документации будут меняться, а старые данные ломать нельзя.

## Файлы

```
geofield/core/schema/
├── README.md          — этот файл (политика миграций)
├── 001_initial.sql    — начальная схема, версия 1
└── NNN_<name>.sql     — последующие миграции, по одной на версию (вперёд-только)
```

## Как это работает

- Версия схемы хранится в `PRAGMA user_version` базы.
- Миграции — пронумерованные файлы `NNN_*.sql`, применяются **строго по порядку** и **только вперёд** (down-миграций нет; откат — из бэкапа).
- Раннер при старте приложения:
  1. читает `PRAGMA user_version` (0 у новой базы);
  2. применяет по очереди все файлы с номером больше текущей версии, каждый — в отдельной транзакции;
  3. после каждого файла выставляет `PRAGMA user_version = NNN`.
- `001_initial.sql` поднимает базу с 0 до 1.

## Соединение

Каждое соединение открывается с:

```sql
PRAGMA journal_mode = WAL;   -- быстрые записи без блокировки чтений
PRAGMA foreign_keys = ON;    -- FK не включены в SQLite по умолчанию
PRAGMA synchronous = NORMAL; -- разумный баланс скорости/надёжности при WAL
PRAGMA busy_timeout = 5000;  -- переживать краткие блокировки
```

> `drift` умеет прогонять эти PRAGMA и SQL-миграции сам; SQL здесь — канонический источник правды о структуре. При генерации Dart-моделей держать их в согласии с этими файлами (ответственность — на `context-keeper`).

## Правила изменения схемы

1. **Никогда не редактировать уже выпущенную миграцию.** Вышла к пользователям — заморожена. Изменение — новым файлом `NNN+1`.
2. **Не ломать старые данные.** Новые колонки — `NULLABLE` или с `DEFAULT`. Переименование/удаление — через промежуточную миграцию с переносом данных.
3. **Совместимость с синхронизацией.** Меняешь пользовательскую таблицу — реши, как изменение отражается в `change_log`/`record_history`, и зафиксируй у `context-keeper`.
4. **Служебные поля — на каждой пользовательской записи:** `author_id, created_at, modified_at, version, sync_status, deleted`. Новую таблицу без них не заводить.
5. **Мягкое удаление.** Пользовательские записи не удаляются физически (`deleted = 1`), чтобы синхронизация донесла факт удаления.

## Инварианты, которые проверяет `logic-auditor`

- `core_intervals`: `depth_to >= depth_from`, интервал не за забоем (`<= boreholes.total_depth`), без разрывов/нахлёстов внутри одной скважины.
- `samples.status`: только переходы `collected → packed → sent → result_received`.
- Любая мутация пользовательской записи → запись в `change_log` и инкремент `version`.
- `sample_results` привязывается к существующей `samples.id`; несостыковки по штрихкоду — в разбор, не молча.
