# GeoField — мастер-план проекта

Управляющий документ. Связывает остальные и перечисляет **всё, что должно быть спланировано** — не только сам продукт, но и стройку, деньги, право, данные и риски.

**Карта документов:**
- `geofield-tz.md` — что за продукт (концепция, стек, данные, синхронизация, дизайн, экраны, оптимизация, конфигурация устройств).
- `geofield-agent-build.md` — как его строить (флот агентов, состязательная проверка, барьер заглушек).
- `geofield-master-plan.md` — этот файл: вехи, команда, право, данные, дистрибуция, деньги, риски, метрики.

---

## 1. Видение и границы

**Что это.** Автономный полевой инструмент сбора первичной геологической информации для малых партий и одиночек, который не теряет данные, бережёт батарею и спутниковый канал и сам сводит пробы с лабораторией.

**Чем это НЕ является (фиксируем, чтобы не расползлось):**
- Не заменяет тяжёлый 3D-софт подсчёта запасов (Micromine, ГЕОМИКС, Datamine). Готовит для него чистые данные — и только.
- Не нефтянка (там Petrel и своя вселенная).
- Не геодезия высокой точности (RTK-съёмка — отдельный класс задач).
- В MVP — не многопартийная корпоративная платформа. Сначала один-три человека.

**Честная оценка масштаба.** Сделанный всерьёз, до выгрузки в тяжёлый софт и связки с лабораторией — это многомесячный, реально многолетний проект. Поэтому он порезан на этапы, каждый из которых полезен сам по себе. Прагматичный первый ход: **внутренний инструмент для своей же партии/компании**, а не сразу рыночный продукт.

## 2. Этапы и вехи (с критериями готовности)

### Этап 1 — MVP «электронный полевой журнал»
**Содержание:** офлайн-карта, точки наблюдения, пробы со штрихкодом, фото, локальная база, автосохранение, валидация на лету, выгрузка в CSV/Excel. Один человек, одно устройство.
**Готово, когда:** геолог проходит реальный маршрут, фиксирует точки и пробы без бумаги, вечером выгружает корректный файл; за весь день ни одной потери данных при принудительных перезапусках/разрядке.

### Этап 2 — синхронизация и партия
**Содержание:** журнал изменений, relay-узел, дельта-синхрон по тонкому каналу, несколько геологов в одну базу, разрешение конфликтов, десктоп-камералка (таблицы, контроль целостности).
**Готово, когда:** трое работают параллельно, данные сводятся без затирания; синхрон проходит через спутниковое окно с обрывами и возобновлением; объём сеанса — сотни КБ, не МБ.

### Этап 3 — керн и лаборатория
**Содержание:** полноценная документация керна (интервалы, выход, истинные углы), печать бирок, ведомости отправки, приём результатов из лаборатории с автопривязкой по штрихкоду.
**Готово, когда:** скважина документируется без разрывов/нахлёстов интервалов; результаты из лаборатории сами ложатся на свои пробы, нестыковки подсвечиваются.

### Этап 4 — мост в тяжёлый софт и зрелость
**Содержание:** выгрузка в форматы Micromine/ГЕОМИКС, разрезы, карты опробования, ОТК/QA-QC, роли, аудит.
**Готово, когда:** выгрузка открывается в тяжёлой системе без ручной правки полей.

### Этап 5 — масштаб
**Содержание:** свой сервер для корпорации, права, многопартийность, модель монетизации.
**Готово, когда:** новая партия разворачивается без участия разработчика.

## 3. Детальный чек-лист MVP (этап 1)

- [ ] Локальная база SQLite (WAL), схема версионируется, миграции.
- [ ] Автосохранение после каждого поля; устойчивость к убийству процесса.
- [ ] Офлайн-карта (MapLibre), скачивание регионов заранее, кэш с лимитом.
- [ ] Текущая позиция, точность GPS цветом, ручной ввод координат.
- [ ] Системы координат: WGS-84, СК-42, Гаусса-Крюгера, МСК; пересчёт внутри.
- [ ] Точка наблюдения: форма с блоками, справочники с подсказками, свободные поля.
- [ ] Структурные замеры: ручной ввод + снятие с датчиков (с предупреждением о помехах).
- [ ] Проба: тип цветом-семантикой, автопривязка, автономер, штрихкод/QR.
- [ ] Фото: привязка к точке/пробе, координаты, миниатюры, отдельная очередь.
- [ ] Журнал маршрута: список, фильтры (черновики/ошибки), поиск по номеру.
- [ ] Валидация на лету: нельзя ввести противоречие, обязательные поля.
- [ ] Режимы: «день на снегу», «перчатки», масштаб шрифта.
- [ ] Авторежим экономии батареи.
- [ ] Выгрузка в CSV/Excel без потери полей.
- [ ] Сборки field / dev раздельно.

## 4. Команда и роли

**Люди (минимум):**
- Ведущий разработчик/архитектор (вероятно, ты) — решения, оркестрация агентов, сборка.
- Геолог-консультант — носитель предметной правды: формы, нормы, реальные сценарии поля. Без него продукт уедет в фантазии. **Критическая зависимость.**
- Тестировщик в поле — кто прогонит на реальном маршруте в реальных условиях (мороз, нет связи).

**Агенты (см. `geofield-agent-build.md`):** оркестратор, архитектор, реализаторы, критики (разрушитель, аудитор логики, охотник за заглушками, аудитор производительности, безопасник), тестировщики устройств, рефакторщик, хранитель контекста.

**Риск одного человека (bus factor).** Если всё на одном — документировать решения, держать чистую кодовую базу, не плодить «магию, которую понимает только автор».

## 5. Журнал технических решений (чтобы не передумывать по кругу)

| Решение | Выбрано | Почему | Отвергнуто |
|---|---|---|---|
| Движок интерфейса | Flutter | Зрелая мобильная часть, свой рендер (нешаблонный вид), все 6 платформ | Tauri 2 (мобилка догоняет), Compose MP (запасной) |
| Локальная база | SQLite + drift | Стандарт офлайн, гигабайты, все платформы | — |
| Синхронизация | Свой журнал изменений | Контроль над тонким каналом, возобновляемая дельта | PowerSync (если нужно быстрее стартовать) |
| Карты | MapLibre GL | Открытый, офлайн-тайлы, без вендора | Платные ГИС с обязательной сетью |
| Сервер | Postgres за relay-узлом | Защищённый контур + публичная точка приёма | Прямой доступ поля в камеральную базу |
| Конфликты | Последняя запись + история + ручной разбор | Простота; совместное редактирование редкое | CRDT везде (избыточно) |

Каждое изменение этого журнала — с датой и причиной.

## 6. План тестирования

- **Модульные тесты** — логика валидации, пересчёт координат, расчёты по керну (выход, истинные углы), сборка/разбор дельты.
- **Интеграционные** — полный путь «ввод → база → синхрон → приём на сервере → выгрузка».
- **Тесты тонкого канала** — искусственно режем скорость, рвём связь на середине, проверяем возобновление и что объём в пределах бюджета.
- **Тесты на реальных устройствах** — Android и iPhone (через соответствующих агентов): GPS, камера, фон, разрешения, печать бирок.
- **Полевая обкатка** — реальный маршрут, мороз, перчатки, нет сети, разрядка. То, что не ловится в эмуляторе.
- **Регресс бюджетов** — холодный старт, память, расход батареи против цифр из раздела 10 ТЗ. Превышение = провал.

## 7. Данные: безопасность, резервирование, приватность

- **Шифрование на устройстве** — база и фото зашифрованы; потеря телефона в тайге не должна означать утечку данных по недрам.
- **Резервирование** — мастер-база (Postgres) бэкапится по расписанию; на устройстве данные не удаляются до подтверждённой синхронизации.
- **Журнал аудита** — кто/что/когда менял, неизменяемый, для ОТК и доверия.
- **Персональные данные (152-ФЗ).** Имена сотрудников, учётные записи — это ПДн. Минимизировать сбор, хранить в РФ, оформить согласия и политику. **Сверить актуальные требования перед запуском.**
- **Данные по недрам** — могут быть коммерческой тайной/собственностью недропользователя. Чётко зафиксировать, кому принадлежат собранные данные (компании, не разработчику приложения).

## 8. Юридическое и соответствие

- **ГОСТ-формы.** Полевой журнал, ведомости, отчётные формы — по действующим образцам, а не вольный перевод. Уточнить конкретные нормы у геолога-консультанта.
- **Реестр российского ПО (импортозамещение).** После ухода Micromine у отечественного софта реальный спрос и преференции при госзакупках. Включение в реестр — потенциальное преимущество, но со своими требованиями (российское юрлицо, исходники, отсутствие запрещённых зависимостей). **Проверить текущие условия отдельно.**
- **Лицензия на сам продукт.** Решить заранее: открытый код / закрытый / двойная лицензия (бесплатно одиночке, платно компании).
- **Сторонние компоненты** — проверить лицензии всех библиотек (MapLibre, SQLite-обвязка и т.д.) на совместимость с твоей моделью распространения.

## 9. Развёртывание и дистрибуция

- **Android** — прямой APK для своей партии или закрытый трек; для рынка — магазин.
- **iOS** — TestFlight или корпоративное распространение, если в App Store не идём; учитывать его правила, если идём.
- **Десктоп** — подписанные сборки (нотаризация на macOS, сертификат на Windows), автообновление **только по нормальной сети, никогда на спутнике**.
- **Обновления в поле** — осознанный жёсткий контроль: полевые устройства не обновляются автоматически в разгар вахты; обновление — плановое, проверенное, по сети.

## 10. Бизнес-модель (если за пределы своей компании)

- **Бесплатно** — одиночка/студент (полевой журнал на одном устройстве).
- **Платно за партию** — синхронизация, камералка, несколько человек.
- **Корпоративно** — свой сервер, права, поддержка, выгрузки в тяжёлый софт.
- **Прагматичная альтернатива:** сначала вообще не продукт, а внутренний инструмент Сусуманзолото/своей партии. Обкатать на реальной работе, потом думать про рынок.

## 11. Бюджет и ресурсы (что потребует денег/времени)

- **Серверы:** relay-узел (твой fly.io-баланс на старте), Postgres-хостинг.
- **Подписи кода:** сертификат Windows, участие в программе Apple (если iOS-дистрибуция).
- **Железо для тестов:** хотя бы один реальный Android и один iPhone, желательно слабый телефон (проверка на нижнем крае).
- **Принтер этикеток** для бирок проб (полевой bluetooth-принтер).
- **Время** — главный расход. Реалистично оценивать каждый этап и не обещать себе MVP за выходные.

## 12. Реестр рисков

| Риск | Влияние | Что делаем |
|---|---|---|
| Незрелость движка на какой-то платформе | Средн. | Flutter выбран ради зрелой мобилки; десктоп проверяем рано |
| Хаос форматов лабораторий | Высок. | Гибкий импорт-маппинг, не хардкод одного формата |
| Старые бумажные данные не привязываются | Средн. | В MVP не лезем; отдельный этап |
| Полевики не примут (привычка к бумаге) | Высок. | Обкатка с реальным геологом с первого этапа; проще бумаги, а не «современнее» |
| Граничные случаи синхронизации (потеря/дубль) | Высок. | Барьер логики у агентов, тесты тонкого канала, история версий |
| Один разработчик выпал | Высок. | Документация решений, чистый код, без «магии» |
| Соответствие ГОСТ/152-ФЗ неверное | Средн. | Консультант + проверка норм до запуска, не после |
| Заглушки доехали до поля | Высок. | Жёсткий барьер охотника за заглушками (док 2) |
| Спутниковый канал съеден фото | Средн. | Фото — отдельная отложенная очередь по умолчанию |

## 13. Метрики успеха

- **Ноль потерь данных** за вахту (главная).
- **Время на первичку:** сколько сэкономлено против «бумага → Excel → база» (цель — убрать двойной-тройной перенос).
- **Доля проб с корректной автопривязкой результатов** из лаборатории.
- **Надёжность синхронизации:** доля сеансов, дошедших без ручного вмешательства.
- **Объём трафика** на сеанс — в пределах бюджета.
- **Принятие:** геолог сам выбирает приложение, а не бумагу, к концу вахты.
